# Audit of 2026-11-10: what was found and not yet fixed

## What this page is

On 2026-11-10, twenty-one reviewers read through the game runtime, the online server, the editor, the Forge tools and the importers. They only read code. They changed nothing and ran nothing.

Over eighty of the problems they found were fixed that day. Those are listed in the [development changelog](../editor/changelog/0.99.5.md) under "Audit of 2026-11-10".

This page holds the rest: problems that were found and left alone. Each was left because it needs one of three things: more than a one-line change, a decision from the owner, or a look in the running game first.

The page has four parts:

1. **For the owner to decide** (6 questions). These are the only part the owner needs to answer.
2. **Bugs** (31 entries, by part of the app). For work sessions.
3. **Slow spots and memory** (11 entries). For work sessions.
4. **What was read and what was not**, at the end.

Remove an item when it is done.

### Three things to know when reading

- **Nothing here was seen in the running game.** Every item comes from reading the code. Unless an item says otherwise, the reviewer followed the code from start to end and is confident. Where an item says "plausible" or "not re-checked", one step on the way was not checked.
- **The next day's audit closed part of this page.** The audit of 2026-11-11 fixed 14 whole items from this page and parts of five more. They have been taken out. They are listed in the development changelog under "Audit of 2026-11-11". What that second audit found and left is in [AUDIT-2026-11-11.md](AUDIT-2026-11-11.md). The six questions below were not touched by it.
- **Where to find the code.** The file name and line at the end of an item say where the problem is. Line numbers are from runtime 20261110.10 and have moved a little since.

## For the owner to decide

Answer by number, for example "1: yes" or "3: leave it". **Answered on 2026-11-12: "all as recommended".** 1 stays as it is. 3, 4, 5 and 6 are done ([0.99.6 development changelog](../editor/changelog/0.99.6.md)); 5 is server code that has only been through a parser and needs a deploy and the server test. 2 is done as worded, and changes little: most model files leave out the format's default, so they say nothing and stay as they were. 6 no longer applies: the 2D Character Generator, the only tool that ran a project's part files, was retired the same day.

Each gives the choice, what it would change, and a recommendation added on 2026-11-12 from reading, not from running the game.

1. **Should fixed, top-down and isometric cameras also move in when a wall or roof is in the way?**
   Today only the third-person and first-person cameras do. A fixed, top-down or isometric camera that follows the player stays where it is, even when a building hides the player. The fix is one line. But it changes how such maps look wherever a building stands between the camera and the player.
   (The wall check looks for a value the camera never gives it: `keepOutOfWalls` in `reactor_3d.js` tests `resolved.focus`.)
   **Recommended:** No. These cameras are chosen for a fixed look, and moving them breaks it. If a hidden player turns out to be a problem, make the wall see-through instead.

2. **Should a model's colour picture repeat past its edges, as the model format says it should?**
   Today the game stretches the edge pixels instead of repeating the picture. The glTF format's default is to repeat. Built characters that were merged into one mesh already repeat. Following the format would change model parts that rely on a tiled picture. It could also show seams on models that pack many pictures into one sheet.
   (`_loadGlbTexture`, `reactor_3d_models.js:3848`.)
   **Recommended:** Follow the file where it says how to repeat, and keep today's behaviour where it says nothing. That gives tiled pictures to models that ask for them and no new seams on the rest.

3. **Should holding the mouse button down keep the player walking?**
   Today a held click walks to the first tile clicked and stops. The walk is aimed again only when the pointer moves. Stock RPG Maker aims again every frame, so holding the button near the edge of the screen keeps the player walking as the map scrolls.
   (`reactor_scenes.js:960`.)
   **Recommended:** Yes. It is what players of RPG Maker games expect.

4. **Should a quest with the "start" rule stay reset after a Reset Quest?**
   Today it comes back one frame after it is reset, and its rewards can be given a second time. The line that causes this looks deliberate. It may be there so that quests added to the Database after a save was made still appear in that save.
   (`reactor_quests.js:590`, `appear = starting || true`.)
   **Recommended:** Yes, it should stay reset: rewards given twice is a bug. Keep "a quest added later appears in an old save" by a rule of its own.

5. **Should online parties, invitations and challenges be tied to the account, not the character's display name?**
   Today the server keeps them by display name. A name is safe while its account is online, or when the account is registered under that same name. But take a character called "Aria" played by the account "doug". While doug is away, anyone can take the name "Aria", and with it Aria's party chat and place in the party. Tying parties to accounts fixes this. It means changing the data the server keeps.
   (`api.php`.)
   **Recommended:** Yes, and before the demo is shown to anyone. It is the one item here that lets a stranger take something from a player.

6. **Should the Forge ask before it runs code that came with a project's character parts?**
   Today, when the Forge opens, part files of the 2D Character Generator that belong to the project run as code, with no question. Project Tools does ask first.
   (`CharacterGenerator.js:239`, `new Function`.)
   **Recommended:** Yes, with the same question Project Tools asks.

## Bugs

### In the game

- **Scrolling a long quest in the quest log blanks its text.** The mouse wheel also does nothing there. (The quest window replaces the scroll function with one that takes different inputs: `reactor_quests.js:1043`, `scrollBy`.)
- **Motions from the motion library lose their arm aims in the game.** Sword Swing and Bow do not move at all. The stretch motion `hamstringStretch` stops with an error for the same reason. (The code that works out the resting skeleton passes no finger joints, so the hands are never found: `libraryRestSkeleton` and `handFrames`, `reactor_3d_motions.js:1330` and `:1867`.)
- **Feet slide about 15 cm during a squat.** The game keeps only the up-and-down part of the hips' movement in a motion and drops the rest. (`reactor_3d_models.js:6396`.)
- **Crossing a map border can throw away materials that are still being drawn.** The materials of the party and of a ridden vehicle stay on the list of the map that was left. When that map's world is removed, they are removed with it. This may also add to the short pause at a crossing. (`reactor_3d_models.js:13338`, `reactor_3d_surround.js:1623`.)
- **Two events that use the same model with different textures look alike.** This affects OBJ, FBX, STL and 3MF models. The game remembers loaded models by a name that leaves the texture out. (`reactor_3d_models.js:126`.)
- **A neighbouring map's glowing water has its haze in the wrong place.** Once the player walks onto that map, the haze sits a whole map's width or height away from the water. (`reactor_3d_world.js:4675`.)
- **Flat wall tiles can be drawn with roof art, and short wall columns can mark the wrong cells.** Two faults in the 3D tile code. Both came from a small test build a reviewer made, and were not re-checked.
  - Every flat wall autotile of the A4 sheet has its art swapped for its roof art, whether it is raised or not. (`roofCapFor`, `reactor_3d.js:5432`.)
  - The table of building fronts marks the wrong cells for a wall column that is shorter than its region. (`reactor_3d.js:6038`.)
- **Battle Room: two faults.**
  - An Action Sequence can land its damage with no motion and no animation. This happens when the routines it calls leave it with no "Apply" step, or with two. (`reactor_battle_presentation.js:924`.)
  - The phase camera does not frame the other sides when a battle has more than two sides. (`reactor_fight_camera.js:1333`.)
- **Three event command settings do nothing.** The dialog saves them and the game never reads them: Spawn Unit's "How many", Spawn Unit's "Stays on the map", and a goal's "Shown as" text.
- **Database, System 1, "Enable Message Skip" does nothing.** The runtime has none of the message-skip code that RPG Maker MZ 1.10 added.
- **A character flash never shows on a character drawn as a 3D model.** It also lasts too long: as many times longer as the character's sprite is slowed down to save work. (`reactor_sprites.js:7492`.)
- **A game that restarts itself on Windows may lose track of its folder.** This is the restart that moves the game to a faster graphics backend (`ReactorBackend`). It may happen when the game was started with one more plain argument. Plausible only: it depends on what NW.js reports in `nw.App.fullArgv`, which was not checked. (`reactor_main.js:406`.)

### Online play

- **Waking up can put a player past an event with the wrong switches.** Waking loads the last full save, which can be up to a minute old. It then places the player where the newest short note says, which is at most five seconds old, on another map if need be. So a player can wake beyond a one-way event while their switches are still from before it. (`reactor_online_ui.js:139`.)
- **The Engine can undo a move that an event made.** The Engine is the real-time server of Engine mode. It refuses a second game-made move of the same player within one second. The game obeys by moving the player back, in the middle of the event. (`engine.cjs:183`.)
- **Real-time battle messages can fail to reach a player.** When the sender has a live socket, messages go only through the Engine's relay. The receiver may have no socket. (`reactor_online_action.js:24`.)
- **`/follow` can take the follower anywhere.** The follower is transferred to whatever place the followed player's game reports. Only the existence of the map is checked. (`reactor_online_party.js:124`.)
- **A stranger can fill a battle's log.** One request can still write up to 16 KB of "join" lines into a battle's log (cut that day from 64 KB). When the log is too big, the server answers "too large" (error 413) and the host's game silently drops it. There is no limit on joins per network address, or on battles opened per player (`bOpen`). (`api.php`, `reactor_online_battle.js:152`.)
- **The server's master secret is sent with every call to the Engine.** It goes to whatever program is listening on the Engine's local port. On a shared host, another customer could listen on that port while the Engine is stopped and take the secret. The Engine should have a key of its own. (`common.php:550`.)

### In the editor

- **Two computers can open the same project and overwrite each other.** The project lock cannot see an editor running on the other computer. Through Dropbox, both open the project and each saves whole files over the other's. The suggested fix: record the computer's name in the lock, and ask. (`ProjectController.js:157`.)
- **Builds: five faults.** (`build-worker.js`, `BuildManager.js`, `DistEditorManager.js`.)
  - A build puts a whole copy of the game in the system's temp folder. On the desktop that folder is memory, not disk.
  - Cancel stops the build without cleaning up, so that copy stays until the computer restarts.
  - An output folder placed inside the project is swallowed into the next build.
  - The previous build is deleted before the new one exists.
  - After each deploy that packs files into archives, the old archives stay on the server.
- **One "Unsaved Changes" answer is given to everyone waiting for one.** Example: the editor asks about the map and the author answers "Discard". If a request to close the editor arrived in the meantime, it gets the same answer, and the Database's edits are discarded too. (`UIManager.js:931`.)
- **Ctrl+C and Ctrl+V on the map canvas copy and paste the whole map.** Delete was already limited to the map list; these two were not. (`UIManager.js:719`.)
- **Plugin Manager: six faults.**
  - It saves its own plugin list over one that the Database's quest log page has just rewritten. This affects projects that use the VisuStella quest log. (`PluginManager.js:128`.)
  - A parameter with no saved value is shown but never written.
  - A parameter whose `@parent` is unknown is never drawn.
  - An empty list or struct value cannot be opened in the Structure view.
  - A translated struct block replaces the English one. (`PluginAnnotations.js:116`.)
  - A stored empty number becomes "0". (`PluginParamCodec.js:47`.)
- **Map Properties clears a battleback name that is not in the folder listing.** (`ProjectController.js:2272`.)
- **Database: eleven faults.**
  - 3D shape edits on the Tilesets page are written to disk at once, so Cancel cannot take them back.
  - Undo on a list restores the whole section from an old copy, and loses the edits made since.
  - A record pasted from another project keeps the old record's 3D model.
  - Change Maximum on User Interfaces can remove a record that System still points to.
  - The Troop and Common Event lists keep old names after an edit.
  - "Referenced by" misses most uses of an Action Sequence.
  - Trait percentages with decimals are shown rounded, and then saved rounded.
  - The tile size choice changes the open map at once, and Cancel does not put it back.
  - A Quests switch cannot be set back to none.
  - Battle Test's Cancel keeps the party edits.
  - Just drawing some pages writes default values. Cancel then asks about changes nobody made.
- **Event Editor: five faults.**
  - A Shift-click selection that crosses a block's Else or End deletes the whole block.
  - Edit on If Win, If Escape or If Lose under Start Battle on Map opens an unrelated Battle Processing dialog.
  - "Editing" a Loop whose contents cannot be read replaces it with an empty loop.
  - Unticking Else, or removing a choice, deletes that branch without asking.
  - The editor remembers which plugin commands are expanded by row number, so the wrong rows open after rows are added or removed.
- **Map editors: eight faults.**
  - A stamped structure's multi-part lamps share one fixture with every other stamp of it. (`StructureCapture.js:104`.)
  - Changing what a light is attached to does not convert its position.
  - Dragging across the two halves of a B to G tile sheet in the palette selects the wrong block.
  - The first stroke that groups 3D objects on a map with no 3D data file cannot be undone.
  - The Event Model card places a model by a different rule than the 3D view.
  - Structure models are not redrawn in 3D after a stamp or a delete.
  - A stroke that changes nothing still empties Redo.
  - Terrain brushes and the 2D pencil paint once per pointer event, so a fast drag leaves gaps.
- **Builds for online games: two faults.**
  - A build made without Online Server ticked never writes the online settings into the game. The game now adds the address prefix itself; the rest is still missing.
  - With "Specific version" chosen for NW.js, a web-only build stops when the computer is offline. (`BuildManager.js:846`.)
- **Prop Builder: four faults.**
  - Exporting a prop again keeps old settings in its `model.json`. For example, a staff no longer set to cast light still does. The export also replaces rules made on the 3D Models page. (`PropBuilder.js:1443`.)
  - A sprite sheet export carries on while the prop is being edited, or after the builder is closed.
  - Export Picture comes out without tone mapping, so its colours differ from the preview.
  - A prop or group named `..` writes its folder one level up.
- **Importers.**
  - Faults read from the code:
    - XP tileset tiles past the first 1024 are dropped with no note.
    - XP move-route "Always on Top" becomes Transparent.
    - XP battle commands 337 to 339 keep XP's order of settings.
    - XP Control Variables reads the wrong stats.
    - In 2000 and 2003 games, `\_` (a half space) becomes a pause.
    - Three system sound slots are off by one.
  - Written from memory of the old engines, and to be checked against them:
    - XP durations (doubled in XP, scaled by 1.5 here).
    - Fade Out BGM in milliseconds.
    - How a map inherits its music.
    - A state's HP change type.
    - Turn conditions of the form `a×X + b`.
  - A damaged record number in a `.ldb` file, or a troop that names itself as its parent, can send the importer into an endless loop.
- **Pop-out windows: three faults.**
  - The right-click menu, the colour popup and the context menu are kept inside the main window's size, not the size of the window they are in.
  - A dropdown stays where it was when its form scrolls.
  - The wait on Structures, Build treats a popped-out Database as already closed.

## Slow spots and memory

Measured or estimated from the code. None was timed in the running game unless it says so.

- **Shadows.** Redrawing one row of still shadows, or one slice of the sun's shadow, goes through every still shadow-casting object on the map. This runs on the main thread, which is exactly what a slow processor is short of. The exact fix is written down in [AUDIT-2026-11-11.md](AUDIT-2026-11-11.md); it needs a run of the Demo. (`reactor_3d_lighting.js:7063`.)
- **Mirrors.** Near a mirror or a lake, at full quality, the game still makes new lists every frame: the list of scored mirror surfaces, a matrix per surface per level, and some short lists. The rest of the per-frame waste was removed on 2026-11-11. (`Mirrors.renderLevel` in `reactor_3d_lighting.js`.)
- **Effects.** An effect attached to a point on a model searches the whole model for that point by name, every frame. (`reactor_3d_effects.js:264`.)
- **Models: four costs.**
  - Every material that names a picture decodes its own copy of it. Across the Demo's models that is about 1.2 GB of 3.1 GB, before size caps.
  - A collision mask is a fixed 513 × 513 grid per model and pose, and is never freed.
  - Every bone moved by an animation is copied three times a frame.
  - The check that hides a body's joints with nothing to draw under them (`BareBones`) looks at every body on the same update.
- **Textures.** Each neighbouring map uploads its own copy of the same piece pictures. In 2D it also uploads its own 20 MB tile sheet.
- **Maps: four costs.**
  - A click-to-move that finds no path searches 32 steps in every direction, and repeats the search at every tile. (`reactor_objects_map.js:2277`.)
  - A hidden tilemap still paints every frame.
  - Colour filters rebuild the same matrix four times a frame.
  - Each time a map scene is built, the game asks the disk again for the companion files of its materials.
- **Sound.** A sound effect that is not stored as `.ogg` searches the disk on every play. Every play also reads and decodes the file again.
- **Tactical battles.** Each time the cursor moves one cell, every ground mark is redrawn, and the game works out again which buildings and walls to cut open so the units inside can be seen.
- **Quests and media.** Quest rules and media surfaces make new objects every frame. Screen texts of imported games run their text codes and sort themselves every frame.
- **Editor: nine costs.**
  - Opening the Forge reads 279 style files (76 MB) again every time.
  - Dragging a Build rectangle copies the map's piece list for every cell on every pointer step.
  - Adding one model rebuilds every model on the map.
  - A tile edit rebuilds the whole 3D scene.
  - The Event Editor rebuilds its whole command list on every change. Copy on a page of 4,000 rows takes over a second.
  - New Project copies the template on the window's own thread, so the window freezes meanwhile.
  - Importing N files scans the folder N times.
  - The in-game character creator downloads all 17 clothing pictures before its first build.
  - Export Model builds the character twice.
- **Memory that is never given back: six leaks.**
  - Tile preview textures in the 2D editor are never destroyed.
  - The 3D Models page adds window listeners on every visit.
  - The Character Builder's view keeps every recoloured outfit picture (16 MB each). Its catalogue pictures on disk are never cleaned out (9,328 files on the desktop).
  - The Animation Generator keeps every video frame at full size.
  - Several Forge tools leave document listeners behind.
  - Projectile models and first-person weapon models leave materials on the map scene's list.

## What was read and what was not

**Read in full:** the 3D core and world, lighting, effects, foliage, doors, neighbouring maps, battles (every file), the online client and server, vehicles, followers, quests, the event interpreter, media surfaces, and the importers' readers of the old engines' binary files.

**Read only in part, and worth another pass:**

| File or area | What was not read |
| --- | --- |
| `reactor_mv_compat.js` (the layer that runs MV plugins) | Lines 2538-3470, 4190-4516 and 4695-5940 |
| `reactor_windows.js`, `reactor_scenes.js`, `reactor_sprites.js` | The parts that come from stock RPG Maker MZ were read only as a comparison against MZ |
| `EventManager.js` | About 85% |
| Event commands | The command pickers, and the insides of the stock command dialogs |
| Database: Troop, Common Event, Tileset, User Interface and 3D Models pages | Everything except how they save and how they close |
| `MotionEditor.js`, `ModelRigger.js`, `ModelAutoRig.js` | Not read |
| 3D Character Builder | The creature, hair, cyberwear and species files |
| Prop Builder | Its 55 files, one per kind of prop |
| Animation and Effekseer generators | Their recipes |
| Importers | `RubyTranspiler.js`, `XpDatabase.js`, `VxImporter.js` |
| The 480 ported plugin files | Checked by script only: that they parse, and that they call nothing undefined |
| 3D map editor | `BuildHotbar.js`, `StructurePlan.js`, `MapFoliage.js`, `MapPicker3D.js` |

The audit of 2026-11-11 read several of these; its own list is in [AUDIT-2026-11-11.md](AUDIT-2026-11-11.md#what-was-read-and-what-was-not).
