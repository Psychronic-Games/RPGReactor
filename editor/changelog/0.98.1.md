# RPG Reactor 0.98.1 - 2026-08-11

### Fixed

- **The Web editor can load the map's 3D viewport dependencies.** The checkbox was not disabled; activation failed and immediately unticked it because `MapEditor3D.ensureLibraries()` only knew the desktop path: locate `runtime/` through `process.cwd()`, synchronously read `libs/three.js` and `reactor_3d.js`, and inject their source. WebHost has no Node `process`, and immutable project scripts are hosted assets rather than synchronous virtual-filesystem contents. The Web branch now resolves `project/js/libs/three.js` and `project/js/reactor_3d.js` through `host.assetUrl()`, loads them lazily and in order as classic scripts, shares an in-flight request across rapid toggles, and clears a failed request so it can be retried. Desktop retains its existing filesystem loader. Distribution coverage opens a fresh Web ZIP and verifies both files byte-for-byte against `runtime/` while confirming the outer editor page does not eagerly load three.js.

- **A saved 3D preference cannot make every later project open repeat a crash.** 0.98.0 wrote `map3DView: true` to the global `rr-settings` record before attempting library loading, geometry construction, WebGL2 context creation, shader compilation, or the first render. Deleting the original project therefore changed nothing: every project uses the same NW.js profile preference. Clean activation failure changed only the in-memory field, and a native Chromium/driver exit could not run rollback at all. A new process now migrates saved 3D state to false before the last project can auto-open. Each manual activation durably records false before graphics work and records true only after a complete build and initial render, so even a native exit leaves the next launch in 2D. 3D remains active across maps and projects in the current process, but every fresh process requires an explicit opt-in.

- **3D viewport activation and teardown are transactional.** Concurrent enable requests share one activation instead of creating multiple canvases and orphaning all but the last renderer. Disabling records the desired state and invalidates a pending activation even while scripts or images are loading. Renderer construction, the first rebuild, and the first render are contained; any exception resolves activation as false, restores the PIXI canvas, clears durable state, and reports the reason rather than becoming an unhandled rejection. WebGL2 is checked explicitly because the bundled three.js no longer supports WebGL1, and pixel ratio is capped at 2 to bound framebuffer allocation.

- **The 3D editor no longer creates a second WebGL2 context beside PIXI's.** Checking 3D on the bundled 50x50 Reactor One map could terminate the Windows NW.js process, including when the Windows build ran through Wine, while native Linux remained stable. That platform split follows Chromium's Windows ANGLE/D3D context path rather than map geometry. PIXI 8 explicitly supports sharing its context with Three.js through renderer-state resets, so 3D now pauses PIXI's ticker, renders Three into PIXI's existing canvas and WebGL2 context, and places a context-free overlay above it for orbiting, painting, and event input. WebGL1 is refused without probing or allocating another context.

- **3D renderers and stale map work are released deterministically.** Teardown disposes Three-owned scene and renderer resources without calling `forceContextLoss()` on the shared PIXI context, resets PIXI's cached GL state, restores its dimensions, redraws 2D, and resumes a ticker that was previously running. Project close and database-load failure tear down 3D before destroying the map renderer. Rebuild generations prevent an older map's delayed sheet, parallax, or character loads from committing after teardown or replacing a newer scene. A render exception stops the animation loop and fails back to 2D instead of scheduling another throwing frame at the display refresh rate.

- **The 3D editor preview refuses allocations that can terminate Chromium before JavaScript can catch an error.** The 2D editor supports 512x512 through chunked residency, while 3D still constructs the complete scene at once in ordinary arrays before copying it into GPU buffers. 0.98.1 limits preview construction to 40,000 cells and 400,000 estimated source quads, preserving the measured 200x200 production map while keeping larger or unusually dense maps in 2D with a clear status. Runtime map data and the game's own 3D behavior are unchanged.

- **MV-era PIXI filters no longer produce invalid PIXI 8 shaders during battle snapshots.** The v8 bridge replaced the legacy `filterArea` declaration and its `.xy` size reads with `uInputSize`, but left `.zw` origin reads untouched. Haven's Pixelate filter consequently compiled with an undeclared `filterArea`; the battle-background `Bitmap.snap()` path exposed the lazy compilation failure and then emitted `useProgram: program not valid` every frame. The translator now maps the logical origin to `uOutputFrame.xy`, maps legacy `filterClamp` to `uInputClamp`, handles precision-qualified declarations, and supports whole-vector or component reads. PIXI's six filter-global uniforms are excluded from the plugin `UniformGroup`, preventing zero-valued custom defaults from overwriting the real filter frame, input size, clamp, or output texture. The canonical runtime was synchronized into all local project templates; a real Project3 NW.js render of its bundled `PixelateFilter` completes with no shader messages and `glError: 0`.

- **PIXI 8 tilemap meshes no longer expose a blank, partial, or folded object seam while the camera pans.** `Spriteset_Map.update()` assigned the tilemap origin after `Tilemap.update()` had already synchronized its transform and mesh, so that update processed the previous camera position. The render transform could then detect the current position, repaint by clearing the visible geometry, and leave its newly generated commands dirty until the following frame. The current origin now reaches the tilemap before the child update cascade, and `_addAllSpots()` immediately synchronizes every lower, upper, or plugin-added tile layer before returning.

  One mixed phase remained: the PIXI 8 compatibility bridge also ran the complete plugin-wrapped `Tilemap.updateTransform()` chain from `onRender`, two or three times in a measured Project3 frame. `TF_Billboard` splits tall objects across 19 independently positioned and sorted row layers, so rerunning their positioning while PIXI constructed render groups could briefly fold adjoining rows even though every mesh was complete. Tilemap preparation now runs exactly once from `Tilemap.update()`; Window and TilingSprite retain the generic render hook they still require. A real Project3 mesh-backend smoke test completed a 360-frame diagonal out-and-back pan across 23 mesh layers with one preparation per frame, no hidden or dirty layer, and no fallback.
