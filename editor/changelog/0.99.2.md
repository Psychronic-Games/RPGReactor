# RPG Reactor 0.99.2 (in development)

Work since 0.99.1. The short version is in the [root changelog](../../changelog/0.99.2.md). Runtime **20261027.1**.

### Added

- **Built-in opt-in HDR effect overlay (runtime 20261025.1).** New module `runtime/reactor_hdr_overlay.js`, loaded by `reactor_main.js` after `reactor_managers.js` and required by the game and editor distribution preflights (`build.js`, `build-worker.js`, `dist-editor-worker.js`). `EffectManager.load` requests a `<effect>.hdr.json` sidecar once per effect (cached, including a 404; aborted after 15 s), and `Sprite_Animation.canStart` waits for it. A valid sidecar (version 1, a GLSL ES 1.00 grade that reads `hdr` and writes `tmOut`, six bloom sizes and tints, a `fallback` twin) routes the animation to a shared half- or float-precision target on the Effekseer overlay context: `Sprite_Animation.renderActive` draws ordinary animations in their original order, then each grade group is accumulated, bloomed (7 downsample and 12 blur passes, all skipped at intensity 0) and graded once. Unsupported float targets or a grade compile failure load the fallback; an unreadable sidecar, or a `-hdr` effect without one, fails closed. Targets are allocated lazily, recreated on resize, and dropped on WebGL context loss (`Graphics._listenEffekseerStateResets` / `_restoreEffekseerContext`). `PluginManager.setup` skips an enabled plugin named `ReactorHdrOverlay`, the overlay's earlier standalone form, and passes its parameters to `ReactorHdrOverlay.configure`. Guide: `docs/HDR-EFFECT-OVERLAY.md`. Tests: `hdr-overlay.test.cjs` (14).
- **Editor previews play an HDR effect's graded twin.** The previews have no HDR pipeline, so an HDR effect played raw: ungraded, unbloomed, clipped to white. `RR_loadEffekseerEffectFromFile`, which every animation preview loads through (Database › Animations and its effect file picker, the Skills/Items animation picker, Show Animation's picker, `AnimationPreviewLayer`), now reads the `.hdr.json` sidecar after the effect (so the web host has warmed the folder) and loads the named twin instead, resolved as the runtime does: beside the effect, or from `effects/` when the name has a `/`. Where the runtime refuses an effect (a `-hdr` effect with no sidecar, an unreadable or invalid sidecar) the loader throws with `rrHdrRefused`, and every caller's existing error path disables playback. `RR_isValidHdrSidecar` mirrors the runtime's check. The Database › Animations preview says which happened, under the picture. Two new strings in all 17 locales, machine-assisted and flagged for review. Tests: `hdr-preview-twin.test.cjs` (5), one of which runs the runtime's own validator on the same sidecars; the stub `fs` in `database-session-sequences.test.cjs` gains the `existsSync` the loader now calls.
- **Editor previews draw HDR effects in HDR (runtime 20261027.1).** `reactor_hdr_overlay.js` now holds the light pipeline as `ReactorHdrRenderer` (targets, bloom, grade, composite; one instance per WebGL1 context, no game state) beside the game's adapter `ReactorHdrOverlay`, which keeps one renderer for the overlay context and is otherwise unchanged. The game's HDR output was checked bit-identical before and after the split on this machine's GPU: the real `api.render` path, five cases (two grades, two sizes, the OT2 grade and a simple one, bloom off), a fixed HDR pattern in place of Effekseer. The composite takes an optional viewport (a cropped view), `alphaFromColor` (alpha from the graded colour, for a premultiplied canvas) and `bloomWidth` (the width the bloom radii are fractions of: the game screen's width as a preview draws it, so a 960x540 preview of an 816x624 game blooms at 706 pixels, not 960); the game sets none of them. New `src/utils/HdrPreview.js` (`RRHdrPreview`) loads the runtime file into the editor, keeps only `ReactorHdrRenderer`, and gives each preview context its own renderer: `load` decides HDR, twin (with a reason in the console: scene-owned 3D effect, no float targets, grade does not compile, renderer unavailable) or refusal, and `draw` runs a frame through the light buffer and screens it over the canvas. All five surfaces load through it and release it with their context: Database › Animations and its effect file picker, `AnimationPickerModal`, the Show Animation picker, and `AnimationPreviewLayer` (premultiplied canvas, light buffer the size of the full view when cropped; GPU effects drawn by the 3D scene keep the twin). Database › Animations' note gains an HDR state, and an **HDR** checkbox beside Repeat switches an HDR effect between HDR and the twin the game falls back to, live: a playing preview reloads and plays on from frame 0, an idle one waits for Play. It shows only where switching changes something (not for ordinary effects, refused ones, or effects that cannot draw HDR anyway), and the choice is remembered per editor in `localStorage` (`rr-animation-preview-hdr`, read and written under `try`; HDR stays on when storage is unavailable). Two new strings in all 17 locales ("HDR" stays "HDR"), machine-assisted and flagged for review. The bloom threshold below moved into the renderer with the rest, checked bit-identical to its own branch in nine cases (four with a threshold, setup levels 0, 1 and 2); a preview places the setup level by its pixels per game pixel (`pixelScale`), so it thresholds at the game's scale. Guide section "Editor previews". Tests: `hdr-preview-render.test.cjs` (9). Three existing tests follow the new routing without losing what they hold: `animation-preview-playback` finds the picker's load in `RRHdrPreview.load`, `animation-preview-fidelity` checks the begin/end pair on both the plain and the HDR draw, and `map-effect-loop-and-placement`'s sandbox gets a pass-through `RRHdrPreview` for its ordinary effects.

### Changed

- **HDR bloom threshold (runtime 20261025.2).** An HDR sidecar may give `bloom.threshold`, UE 4's bloom setup threshold: the first half-resolution downsample multiplies the light by `clamp((dot(rgb, (0.3, 0.59, 0.11)) - threshold) * 0.5, 0, 1)`, as `PostProcessBloomSetup` does, so light at or below the threshold does not bloom. Without it every pixel blooms, as before. The editor's sidecar check (`RR_isValidHdrSidecar`) accepts the same field; a non-numeric threshold fails closed in both. Tests: `hdr-overlay.test.cjs` (17), `hdr-preview-twin.test.cjs`.
