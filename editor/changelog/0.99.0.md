# RPG Reactor 0.99.0 - 2026-10-12

This release carries the unreleased 0.98.9 work forward. Add further work for the upcoming weekend release here.

### Added

- **Show Text preview draws `\FontChange<x>` in that font (PR #74, Xehanort88).** The preview and the width guide read only `\X[n]` codes, so MessageCore's `\FontChange<CDread>` was drawn as literal markup and measured as nine glyphs. The name is now resolved as the game does: the families FontManager registers (`rmmz-mainfont`, `rmmz-numberfont`, MessageCore's Custom Fonts through `TextCodes.customFonts`) load from the same file under `fonts/`, any other name passes through as a CSS family, and `\ResetFont` restores face, size and color. Face, size and color carry down a box instead of resetting each line (`scanMessageLine`'s `pen`), and the guide no longer measures any code's `<argument>`. Merged on GitHub and brought in by merging its main; the one conflict, in `renderMiniPreview`, keeps both the speaker picture and the font version in the miniature's key.

- **Web builds in pack archives.** Owner, 2026-10-11: "a way for the project to read a zip file with multiple files in it and use it like the normal folder structure… to get around these limits". Optional, and named for what it does, not for a storefront.
  - **Builder (`build-scripts/web-pack.cjs`).** `packFolder(root, { keep })` moves files into `packs/pack-N-<hash>.zip` (real zip archives written by hand, no dependency; entries marked Unix-made so tools read UTF-8 names) and writes `packs/index.json`: `files[path] = [pack, offset, stored, size, method]`. A file is deflated when that saves a tenth (data, scripts, GLB models); pictures, music and video are stored, which keeps byte ranges for seeking. No archive passes 150 MB, under a 200 MB per-file limit. Same files, same archives.
  - **Reader (`src/web/pack-reader.js`, in a service worker).** A request for a packed path is answered from its archive by a `Range` request, inflated with `DecompressionStream` when deflated; a `Range` on a stored file is that part of the archive; HEAD is answered from the index. A server that sends the whole archive instead has it put in Cache Storage once (requests that arrive meanwhile wait for it) and cut from there; an old build's archives are dropped from the cache when the index names new ones.
  - **A deployed game (`packGame`).** Everything but the page, `css/`, `icon/` and root files is packed; `reactor_pack_worker.js` (reader + `src/web/pack-worker.js`) sits beside `index.html`, whose head gets a gate: under the worker the page loads as written; on a first visit it brings the worker up and reloads once. (A first design held the page's scripts back and ran them after the worker was up; the game never started, because it starts on the window's `load` event, which had already fired.) Deploy Game › Web (HTML5) › Pack files into archives, remembered (`WebPackPreference`).
  - **The web editor (`dist-editor-worker.js`, `packWebFiles`).** The whole `project/` is packed after the manifest and the file index are written; the reader goes in front of `service-worker.js`, which serves a browser-saved edit first, then the packs, then the server; the manifest says `packed`, and the host says so plainly when a window blocks service workers. Deploy Editor › Web has the same checkbox; `release-editor.cjs --target web --pack-web true` for a release build.
  - **Measured on today's Demo.** Web editor: 1,022 files / 509 MB extracted (over both of a common storefront's limits) to 53 files / 457 MB with packing; data 5.5 to 0.4 MB, scripts 15.5 to 3.5 MB, 3D models 165 to 132 MB, music and pictures unchanged. ### Performance

- **Pieces read once per stored list.** `RRMapElevation.pieces` normalized every piece of the map on each call (33 call sites in the builder), and `pieceGroupAt` did so once per building. - **Measured and left out:** keeping the 2D tile atlas across a menu or battle. On the Deck Drill the atlas costs under 1 ms to make and the return to the map takes 85 to 110 ms with or without it.

- **Game speed below 60 frames a second (runtime 20261009.2).** `SceneManager.determineRepeatNumber` adds frame time up and makes updates as they come due (up to `MAX_UPDATES`, 4, a frame) instead of rounding the smoothed interval, which made one update a frame from 60 down to 40 frames a second (45 updates a second at 45, 48 at 24, 72 at 40). - **Quality levels (runtime 20261009.2).** `Reactor3D.Quality` keeps the frame rate on a machine that cannot draw the full picture: it counts the world frames a second of play delivers against the screen's own refresh, and steps down along GPU levels (render scale 0.83 and 0.67 of the project's, model detail, shadows) or CPU levels (no depth-first draw, thinner foliage, shadows), whichever the frames wait for, then draws the world on every other update. Level 0 is today's picture; a step back up is tried only at a map change. Levels are saved per machine (`ConfigManager.graphicsAuto`), and the player chooses Auto, High, Medium or Low in Options (`ConfigManager.graphicsQuality`, `Window_Options.addGraphicsOption`; the Demo's entry is in its options plugin's Visual category). ### Development

- **The frame harness times frozen frames back to back.** `nw-frame-breakdown.cjs --mode=frozen` slept between timed draws, and an integrated GPU dropped its clock in the gaps: the same frame measured 12.9 to 20.4 ms. It now draws eight frames first and times the rest back to back (±0.1 ms). `--positions=N --gap=S` freezes N places along a `--walk`; `--images` saves each variant's frame; it waits for shader warmup, the light volume and a resting camera before freezing.
- **CI.** The Web persistence smoke is intermittent on GitHub, not broken. On failure it now prints the page state and browser console, and on Actions repeats them as an error annotation, which the public API returns without signing in (`reportSmokeFailure` in `webdriver-client.cjs`). `actions/checkout` and `actions/setup-node` move to v5 (Node 24; v4's Node 20 is deprecated on runners).
- **`reactor_core.js` and `reactor_objects.js` split by class (runtime 20260929.1).** The core (10,700 lines) is now `reactor_core.js` (JS extensions, Utils, Graphics, profiler, events, Point, Rectangle, Bitmap), `reactor_core_display.js` (Sprite to Stage) and `reactor_core_io.js` (WebAudio, Video, Input, TouchInput, JsonEx). The objects (12,800 lines) are `reactor_objects.js` (Game_Temp to Game_Item), `_actions`, `_battlers`, `_map`, `_interpreter` and `_legacy` (the 2000/2003 command equivalents and `[fN]` sheets). Every part is an exact slice of the old file, cut at a section boundary; `reactor_main.js` loads them back to back and the three deploy checks require them. Globals, class names and load order are unchanged, so plugins and imports see the same engine. One hazard, found by loading the parts in a VM: `Window.defaultMargin` was set in the Bitmap section, before `function Window()`, which only worked because declarations hoist within one file (split, a browser would set it on the DOM's `Window` and lose it); it moved into the Window section. `runtime-core-split.test.cjs` loads the parts in order with only PIXI stubbed, so a part reaching a later part's class while loading fails; tests read the source through `tests/helpers/runtime-source.cjs` (`runtimeSource()`, the parts in load order); `SequencePreview` reads WebAudio from `reactor_core_io.js`, or `reactor_core.js` in an unrefreshed project. - **Headless harness displays.** On the headless Wayland compositor (`WAYLAND_DISPLAY=rroracle`) Chromium's GPU process has no hardware GL and runs on SwiftShader, while video still decodes on the real GPU; the decoded frames cannot be imported (`Could not find SharedImageBackingFactory ...
