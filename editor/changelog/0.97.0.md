# RPG Reactor 0.97.0 - 2026-08-03

### Added

- **3D objects are grouped on the map, not only in the tileset.** A tileset says what a *tile* is, and that is all it can say: an autotile id is a corner arrangement shared by forty-eight shapes, so three shops built from one wall kind are the same tile as each other and nothing in the tileset can tell them apart. Declaring a rectangle of a sheet does not help either — an autotile has no place in a drawing to declare. Which cells make up one building is a fact about a *placement*, so it is now said on the map, in a palette tab beside Regions and painted the same way. Cells sharing a number are one object however they are arranged, so a building hacked together from bits of three others is one thing and says so.

  It is per layer, because a tree on B standing over a wall on A is not part of the building; `Auto` paints every layer holding a tile, which is what takes a wall and the signage hung on it in one gesture. A **Footing** brush marks the cells that are the ground an object stands on rather than a course of its height — standing a drawing up turns its rows into courses, so a building painted across seven rows is seven tiles tall and plants itself on its southernmost row unless it is told which rows are the pavement.

  Every tool routes it: pencil, eraser, rectangle, circle and fill, with fill flooding by object number so a structure is grouped in one click. The eraser takes the grouping rather than the tiles under it. It lives in `Map###.r3d.json` beside the map, never in `Map###.json`, so the map stays ordinary RPG Maker data — which matters more here than most places, because MZ's six planes are full and there is no seventh to take.

- **A page set to Custom movement can say what the route is.** Choosing Custom was half of it: the type could be set and there was no way to author the route, so the page kept whatever list it already had and a new event kept an empty one — Custom meant "stand still" and could not be made to mean anything else. A **Route…** button sits beside the dropdown, enabled only for Custom, and opens the same dialog the Set Movement Route command uses, because an autonomous custom route *is* a move route built from the same forty-five commands. Two things the page has already answered are left out of it: the character, since it is always this event, and Wait for Completion, since nothing is waiting on it.

- **Flying the editor's 3D camera.** WASD moves, Q and E change height, Shift hurries. Movement is timed rather than counted, so the same press covers the same ground on any machine, and its speed is judged against whatever is in front of the camera when the flight starts. Orbiting is how you inspect a thing; this is how you inspect a place.

- **A hover outline in the 3D view.** On a flat canvas the cursor is already on the map and where a click lands needs no explaining; through a perspective camera the tile under the pointer is the answer to a raycast, which is not something you can eyeball. The cell is outlined as you move, scaled to whatever brush is in hand, so a three-by-three stamp outlines all nine cells rather than one.

- **Events can be dragged in the 3D view**, as they can on the 2D canvas, with the same refusals: not off the map, and not onto a cell another event already holds. Undo is captured on the first cell actually crossed rather than on the press, so clicking an event to select it does not push a snapshot of the whole event list and wipe the redo stack.

- **Events are drawn in a box in 3D.** An event drawn from a character sheet is a picture standing on the map and nothing about it says it is an event — it reads as a painted tree until you happen to click it, which is why the 2D canvas borders every event. Edges only: a filled box would have to be transparent, and transparent boxes are what sliced the name labels.

- **Escape lets go of whatever is held** — a lifted map stamp first, then a selected event, then the tile palette. Every selection was sticky and choosing something else was the only way out; carrying a stamp is easy to do by accident and it keeps painting on the next click. It stands down while a dialog or a text field is up, so closing a dialog does not silently drop your brush.

- **Clear, in the tileset's 3D Shape editor.** Every other setting there could be changed and none could be removed: Auto reset a tile's class and left its stand-in, its roof pairing and its object membership behind, with no way back short of hand-editing the sidecar. Clear forgets all four for every tile dragged over, works on autotiles — anything that can be classified has to be un-classifiable — and reports honestly, since the accessors return derived facts as well as authored ones and asking them naively marked every tile in the sheet as carrying information. It replaces Remove, which undeclared an object and kept the classes; the two overlapped almost entirely outside one narrow case and did not earn a second destructive button.

### Removed

- **The height brush.** Massing painted per cell was the wrong half of the problem: nothing on a real 3D map uses it, because the massing all comes from the tileset's 3D classes. Its toolbar button, level, action and width controls, undo integration and the 3D view's paint path are gone, along with eleven tests covering them. `MapElevation` itself stays — the runtime still reads elevation and the `<3d>` note from the sidecar — so a map that carries heights is unaffected; nothing writes them now.

### Fixed

- **3D grouping survived a save and not a reopen.** The sidecar was written correctly and nothing read it back: it was attached to the map only when the *3D view* opened, which held while everything in the file was something only that view could show. Grouping is painted on the 2D canvas, so the file has to be in hand whenever the map is. The visible half was an empty overlay; the silent half was worse, because painting again over an unread sidecar and saving writes one built from nothing and takes everything else in the file with it. It is now read as part of loading the map, and a corrupt one is logged and skipped rather than stopping the map from opening.

- **A grouped building counted as no change at all.** The dirty check compares what goes into `Map###.json`, which deliberately excludes the sidecar, so a map whose buildings had just been grouped read as untouched — closing the project never asked, and the work went without a prompt. The check now asks the sidecar too.

- **The Role tool changed nothing that lasted.** It cycled roles in memory and returned without saving, while every other tool in the 3D Shape editor saves — so laying an object's ground rows flat reached neither the file nor the open 3D map, and reopening the project stood them back up. It read as the tool doing nothing at all, which is a poor way to discover that roles are how a seven-row gateway is told which of its rows are the pavement.

- **Fifteen strings in the movement route dialog, and the whole 3D tool palette, were never translated.** The palette's tool names and hints — Select, Flat, Upright, Scenery, Foliage, Panel, Auto, Clear, Object, Role, Roof and every description beside them — were bare literals that went through no translation helper at all, so that palette shipped in English on every locale and the localization gate could not see it. They are routed now, translated into all seventeen non-English locales, and covered by the gate, which follows indirect helpers as well as direct calls.

- **The Region palette could not be scrolled, and neither could the new one.** A flex child defaults to `min-height: auto`, so it grows to fit its content instead of scrolling it: thirty-two rows of swatches in a panel a few hundred pixels tall with no way to reach the bottom. The tileset preview beside it has always said `min-height: 0` for exactly this reason.

- **Both palettes now sit in their panel the way the A-G tabs do.** The tab reveals the panel with `display: flex`, which is a row, so its one child was sized to its content and stopped short of the right edge — a bare strip beside the scrollbar that no amount of styling the canvas could close. They also draw at the project's tile size now, like every tile beside them, rather than at a fixed 48.

- **A region number was drawn at a fixed 18px into a canvas the size of a tile.** At 48 that fits; at 24 it fills the cell edge to edge, and at 16 it is not a number but a smear wider than the cell and taller. Four places drew one — both overlays and both cursor previews — and all four now size the glyph and its outline from the tile. The region overlay's texture cache was also keyed by number alone, so opening a 24-pixel project after a 48-pixel one handed it the previous project's textures.

- **The 3D view kept showing the previous project's 3D checkbox state**, and switching between the Region and 3D object tabs left both overlays drawn at once — two sets of coloured numbered squares over one map, answering different questions, impossible to tell apart.

- **Turning while flying threw the camera around an arc the width of the view.** `orbit` circles the point the camera is aimed at, which is right when you are studying a building and wrong when you are moving; turning now pivots in place. Turns are also banked and spent once a frame, because pointer moves arrive several to a frame and each one moved the camera, so a smooth drag came out as a burst of steps.

- **Orbiting pivoted about a point that had nothing to do with what was on screen.** The camera always looks straight at its target, so the pivot is at the centre of the view — but only as a *direction*. How far along it the pivot sits is the view distance, and nothing kept that honest: framing sets it to about the map's width, and flying then moves the camera without touching it. After a flight the pivot could be hundreds of tiles past everything visible, so a drag swung the whole map about a point out in the distance. A gesture now seats the pivot on whatever the centre of the screen is actually looking at, without moving the camera — the hit lies on its own view ray, so only the distance along that ray is corrected.

- **Cut-outs were built one cell wide however big their art was.** A stand-in names a rectangle of the sheet — a mountain drawn across a 2x2 block — and the span was read as an aspect ratio with its size thrown away, so that mountain was built at the same world width as a single tile. The picture came out squeezed to half its width, and the quad no longer covered the cell it stood on, so bare ground showed between one cut-out and the next: rectangular bites out of a range's silhouette, with the straight vertical sides a billboard quad has. A cut-out is now as wide as its art and as tall in proportion, it is never narrower than the cell it stands on, and its scatter is clamped to the overhang it can afford so a big one still breaks up the grid. On Infernis Prime, 7,515 of 8,550 foliage cells failed to cover their own cell and 3,821 adjacent pairs had bare ground between them, up to two thirds of a tile; both are now zero. A 1x1 stand-in multiplies by one, so ordinary foliage keeps its look apart from that size floor.

- **Star-flagged art wins where it stands in the same place as art that is not.** A column's capital carries the star flag and a plate resting on the same cell does not; both are cut-outs at one anchor, so they are exactly coplanar, and at equal depth whichever is drawn first wins and the other is rejected. Which of them that was came down to the order the meshes happened to be built in, so a capital could end up behind the plate leaning against it — the opposite of what the flag means, which in 2D puts the tile over every ordinary tile in the cell. The starred pass now carries a deeper depth bias, which decides ties between surfaces at the same depth and changes nothing about real occlusion: a column still goes behind a wall a tile in front of it. The runtime draws its two passes separately over a cleared canvas and never saw this; the editor draws the scene in one go, which is where it showed.

- **Standing art turns about its own axis, and stays seated where 2D draws it.** A cut-out's anchor is the point it pivots on, and it centred on the cell across the object's columns but sat on the *southern edge* of its bottom row along the other axis — so the two axes disagreed by half a tile. RPG Maker plants a sprite's feet on the bottom edge of its cell, `screenY` being `scrolledY * tileHeight + tileHeight`, and that had been read as a world position when it is a screen convention. Half a tile of pure depth is invisible head-on, which is why it looked right, and it swings into view as the camera comes round: a column standing in the middle of a three-by-three pool ended up planted on the pool's southern lip. Props, characters and the position plugins are told all take the middle of the cell now — they have to agree, or a character walking up to a column would not meet it.

  Centring the anchor alone then read half a square too far back from the front, because a column standing on a cell fills it front to back and what the eye takes for "where it stands" is the near edge of its base, not the middle. A cut-out has no depth to spread across, and which edge is near changes as the camera comes round, so no fixed world position satisfies both — the southern edge is seated head-on and adrift once turned, the centre is the reverse. The quad is offset half a cell towards the camera instead: the pivot stays the cell's middle, so the object turns about itself, while the visible base sits on the near edge from every angle.

- **Two standing objects can share a cell, as they do in 2D.** A cell has four tile planes and more than one of them can be standing art — a plate set down on a column occupies the same square as the column, and the 2D tilemap simply draws one over the other. The 3D builder asked for *the* upright tile of a cell, was handed the topmost, and threw the rest away: the plate was drawn and the column it stood on vanished, while 2D looked perfectly ordinary. Every standing tile in a cell is built now, lowest plane first so they layer the way the tilemap layers them. The questions that genuinely want one tile — which object a cell belongs to, whether two cells are one picture — still take the topmost, so nothing about grouping changes.

- **A cell can belong to more than one declared object.** A plate set down on a column shares both of the column's cells, and asking the cell's *topmost* tile which object it belongs to read the plate as the whole story — so the capital and the shaft joined the plate's 1x1 instances instead of each other. That made them two objects with two anchors, and a cut-out turns about its own anchor, so the column came apart and its halves swung independently as the camera moved. Each tile answers for itself now: the column's two cells find the same origin and are one object, the plates are their own, and the pieces of a column turn together.

  The star flag goes back to being read per tile, as the 2D tilemap reads it. Answering for the whole object was tried while a column was disappearing, on the theory that its halves were split between the passes; the cause was elsewhere — a cell only ever yielding one standing tile — and the object-wide answer had a cost of its own, putting a column's unflagged shaft in the pass over the characters where it covered a plate standing in front of it.

- **Painting a 3D class in the tileset editor takes effect, and is saved.** The Roof, Clear and Object tools each wrote the classification file when they were used; painting Flat, Upright, Scenery, Foliage or Panel did not. So the change lived only in the editor's in-memory store — not on disk, and not announced — which is why it appeared on the map only after the 3D view was switched off and on, that being what rebuilds from the store. Both the drag tool and the click-to-cycle path save now, once per gesture rather than once per cell.

- The 3D render loop lets go of its frame handle when it stops. `startLoop` refuses to start a second loop by checking that handle, so a tick that bailed while still holding a stale one meant the loop could never be started again — leaving a canvas that drew only when the pointer moved over it, those handlers rendering directly, and otherwise showed nothing.

- **Changes made in the Database reach the open map.** Passability, the star flag and the 3D classification were all edited in place and repainted only the Database's own canvas: the map editor holds the tileset object it captured when the map opened, so a flag change did not take effect until the project was closed and reopened, and a 3D class change did not until the map was next painted. Flag edits now announce themselves — `ProjectController`'s listener was already written expecting exactly that, its comment saying "on every flag edit as well as on an image assignment", and it was simply never sent — and the 3D classification gets an announcement of its own, `rr-tileset-3d-saved`, which the 3D viewport follows. Separate events because they cost different things: a stroke of the Shape tool would otherwise re-diff every sheet and refresh the database list per cell.

- **A project opened with the 3D box ticked comes up in 3D.** The view is a preference rather than a property of the map, and the viewport is torn down when a project closes — so opening another one left a ticked box over a 2D canvas, and only unticking and reticking put the two back in agreement. The controller now reconciles what is showing against what the preference asks for whenever a map comes up with the viewport off.

- **Which layer a tile lands on no longer depends on the tab it came from.** B started at z1, C at z2, D onwards at z3, and the search for a free slot then ran *upwards* from there — so the same object dropped from two tabs sat at two different depths, and a B tile went underneath a C tile for no reason but their names. RPG Maker's own maps settle it: across the bundled projects, of 256,366 cells carrying exactly one B–G tile, **90.8% have it on z3** and 8.9% on z2; of the 45,075 carrying two, **99.8% use z2 and z3 together**. B, C, D and E each sit in those proportions — the sheet makes no difference at all. Every picture sheet now starts at the top of the stack. Which *way* a cell fills is not something those counts can answer — two tiles end up at z2 and z3 whichever order they were laid down in — and it is settled instead by what the map draws: z3 covers z2, so painting one thing over another has to put the new one *above*, or the tile just placed vanishes behind the tile placed before it. So the top slot is always taken and the stack moves down beneath it, which is also what leaves that z2+z3 pairing, older underneath. The terrain slot is preserved however deep the pile gets, and putting something *below* what is already there is what choosing a layer by hand is for. The A tabs keep the ground slot.

  One exception, and RPG Maker has it too: an **overhang keeps its place**. The star flag means "draws above characters" — a canopy, an archway, the top of a doorway — and a plain tile painted into a cell holding one of those slides underneath rather than shoving it down, because the overhang is the thing meant to be in front. The authored maps bear it out: of the 14,066 stacked pairs where exactly one of the two is starred, the starred one is the upper of them 84% of the time. Two overhangs, or an overhang painted over a plain tile, follow the ordinary rule. Coverage in `picture-sheet-layers.test.cjs`.

- **A sheet assigned in the Database is usable straight away.** Assigning one to a slot updated the tileset editor's own thumbnails and nothing else: the map canvas and the tile palette each captured the tileset when the map opened, so neither heard about it until the Save button beside the name was pressed. A sheet added to E, F or G was therefore not selectable in its tab, and a tile placed from one drew nothing at all — the sheet it addresses had never been loaded, which reads as the tile vanishing. Assigning now announces itself the same way saving does. It only announces: writing `Tilesets.json` stays with the Database modal's own OK, so Cancel can still put everything back.

- **Walls cast their shadow, and take it away again.** RPG Maker fills the left half of the cell immediately east of a wall — quadrant bits 0x01 and 0x04 — and clears it when the wall goes. Reactor drew none: the only thing that wrote the shadow plane was the shadow pen, so a wall placed in the editor had no shadow at all, and one arriving inside a pasted stamp brought whatever had been lifted with it whether or not a wall was left to cast it. The rule is read off the authored maps rather than guessed: of 39,104 shadow cells across the bundled projects, 85.6% carry exactly that pattern and much the commonest thing beside a shadow is a wall immediately west.

  It runs on every path that lays a tile down or takes one away — the brush, the rectangle and circle area tools, bucket fill, the eraser and a pasted stamp — and keys off walls *coming and going* rather than off cells being touched — filling a floor beneath a wall that was already standing must not conjure a shadow the author never asked for. Only the two quadrants a wall casts are ever written, so a shadow put in the other half of the same cell with the pen survives a wall being built or removed beside it. A wall casts nothing onto another wall, roofs and ground autotiles cast nothing at all, and a wall on the map's eastern edge casts nothing off it. Coverage in `wall-auto-shadow.test.cjs`.

- **A pasted piece of map rebuilds its autotiles where it lands.** A stamp lifted with a right-drag carries the tile ids it was copied from, and an autotile id is a corner arrangement rather than a picture — so a stretch taken out of the middle of a wall arrived carrying middle-of-wall pieces, with no ends, and read as a wall with a slice cut out of it. The shapes are recalculated on paste now, as RPG Maker does, so the copy comes down as a finished wall of its own; the border is rebuilt too, so pasting against an existing wall joins it rather than leaving both with an end facing the other. **Shift** asks for the ids verbatim, which is what Shift already means when painting a single autotile from the palette — and it now claims the gesture while a stamp is held, where it was previously read as a map pan because the palette selection is cleared when a stamp is picked up. Only A1–A4 are rebuilt: A5 is not an autotile and B–G are pictures, whose ids mean a position on a sheet. Coverage in `map-stamp-autotiles.test.cjs`.

- **Auto-layer ground autotiles replace the ground they are painted over.** Sand painted across water was treated as an overlay merely because it was a different autotile kind: it went onto map layer 2, left the water underneath, and calculated its shape in a layer with none of the surrounding ground. It now stays on map layer 1, replaces the water, and reconnects every painted cell and neighbor there. Decorations still use the second A slot, and distinct A1 water kinds retain their deep-water stacking behavior.

  A tile also **joins the slot its own terrain already occupies beside it** before the fallback is considered. That keeps a repaired upper-layer road on the layer occupied by the rest of its run; moving it there now removes the stale lower copy instead of hiding a duplicate beneath the repair. A lower-layer decoration beside the cursor cannot pull a new decoration down through the floor at its destination.

- **The front of a mountain range stood a tile clear of the ground in 3D.** A connected region of upright cells shares one footing — its southernmost row — so that a wall does not tear in depth when its base is uneven. That footing was deciding *height* as well: a column's art was indexed from it, so a column whose lowest painted cell is north of the footing was drawn that many courses up with nothing beneath it. A range's southern edge steps back in ones and twos, so its whole front row hung. On Infernis Prime 166 of 616 columns hung; across that project's 906 maps, 10,207, some of them twenty-one tiles up.

  The two questions are separated now. The footing still sets the depth, which is what it exists for; height is asked separately, and a column only hangs where something is holding it up — an archway's panel has posts either side, so the rows beneath it are spanned by the same region left and right, while a range's edge has open ground on one side and sits down. Bridging counts only while it is unbroken, so a panel on posts standing on a slope is not read as floating. Across those 906 maps the run count and the number of courses drawn are both unchanged to the unit — no art is dropped or invented, it is only lowered — and hanging columns fall to 2,435, which are the genuine openings.

  The bridging test is reach along a row, so a connected spur of the same region further along reads as support. `reactor-3d-footing-lift.test.cjs` pins that limit as well as the fix: tracing what actually carries a load is the structure question the design notes record as unsolved, and this failure is one column of one shape rather than a whole range's front.

- **Panning past the edge of the map, then jittering back.** Holding the scroll wheel and dragging wrote the container position straight out and left the clamping to `updateScrollbars`, which is throttled to one call a frame — so the view was drawn genuinely outside the map and yanked back a frame later, every frame, for as long as the drag kept pulling. The view is held inside the map as it moves now, so a pan stops at the edge and stays there. The drag anchor is re-read from the clamped position each move as well: clamping alone banks the overshoot in the anchor, and pulling back then does nothing until it has been unwound, which reads as the pan sticking. `panBounds`/`clampContainerToMap` are the single answer to how far the view may travel — the same two `Math.max(min, Math.min(0, ...))` lines had been written out four times, for wheel zoom, the scrollbar thumbs and the scrollbar refresh, and not at all for the pan. Coverage in `map-pan-bounds.test.cjs`, which drives the real pointer handlers.

- **Shift could not extend a 3D object onto a second piece.** It only ever extended an object declared earlier in the same session, so selecting an existing object and shift-dragging the rest of it started a fresh object instead — which is the entire gesture, for a prop that crosses the seam where a B–G sheet's two halves are stacked. It now joins whatever is selected, read before the drag reselects, and a single shift-click onto an existing object is no longer refused.

- **An object anchored at a sheet's first tile could never be extended.** The merge asked `tileAtCell` for the origin and treated a falsy answer as failure — but the top-left tile of sheet B *is* id 0. The edge is checked by bounds now. The same call reported three different failures as one message, so a mismatch that was nothing to do with sheets said "that is on a different sheet"; each says which it is.

- **Dragging off the edge of a tileset claimed rows that were not on screen.** The drag never clamped, so it kept counting past the canvas and declared a rectangle over tiles the author could not see until they scrolled to them.

- The editor assumed 48-pixel tiles. `System.json` carries `tileSize` — MZ offers 48, 32, 24 and 16, and `DatabaseSystem2Editor` already exposed it — and `Game_Map.tileWidth` in the runtime reads it, but `TilemapManager`, `TilesetPaletteViewer` and `DatabaseTilesetEditor` all measured in literal 48s. A 32-pixel project's sheets are two thirds of the standard layout (512x384 where MZ would be 768x576), so every sample landed 1.5 tiles along and drifted, drawing a mosaic of unrelated art. `src/utils/TileMetrics.js` is the single source: `tileSizeOf` validates against MZ's four sizes and falls back to 48, `sheetScaleOf` converts a 48-based measurement. `TilemapManager.TILE_SIZE/WIDTH/HEIGHT` and the palette's `tileSize` are read from it and refreshed by `refreshTileMetrics()` once the database has loaded, since both surfaces are constructed before it. The 48s in tile-id arithmetic are untouched: there 48 means shapes per autotile kind, a property of the format rather than of the art, and a test asserts both that the pixel assumptions are gone and that the format constant survives. `TilesetPaletteViewer.prototype.tileSize` carries the default so an instance built with `Object.create` — which the transparency tests do, to avoid the DOM — still measures in whole tiles. `MapEditor`'s palette sampling, `ProjectController`'s map pixel extents, `MapEditor3D`'s character frames and raycast quadrant offsets, and `Reactor3D.MapScene.build` (via `Reactor3D.currentTileSize`, which reads `$dataSystem` the way `Game_Map.tileWidth` does) were converted in the same pass. `DatabaseSystem2Editor` calls `window.rpgReactorTileSizeChanged`, which `main.js` binds to re-read every surface and reload the open map, so the setting takes effect where it is made. Coverage in `tile-size.test.cjs`, including a sweep over all six renderers that fails on any bare pixel 48 while allowing stated `|| 48` fallbacks and the format's `% 48` / `2048 + kind * 48` arithmetic — the sweep is what caught the three sites in the tileset editor's autotile palette that a by-hand list had missed.

- The tileset editor's overlay marks were measured for a 48-pixel cell and did not fit a smaller one. The passage arrows sit a fixed 8 pixels in from each edge, so on a 16-pixel tile the left and right markers landed on the same point and all four directions read as one blob; a ladder icon 16 pixels tall starting 4 down ran into the tile beneath it; and the 3D class marks are sized as `tileSize - 26`, which at 16 and 24 is negative — and `fillRect` with a negative width draws *backwards*, into the neighbouring tile, rather than clipping away. `markScale()` brings the marks in with the cell below 32 and is capped at 1, so 48 and 32 are untouched: the marks are deliberately not shrunk down to 32, since one nobody can read is worse than one that is slightly large. Coverage in `tile-size-overlays.test.cjs`, which drives the real overlay through a recording canvas at all four sizes and holds 24 and 16 to the proportions 32 already has.

- Tile-size support is now checked by running the renderer rather than by reading it. `tile-size.test.cjs` sweeps the source for bare pixel 48s, which cannot tell a right formula from a wrong one built out of `TILE_WIDTH`. `tile-size-rendering.test.cjs` loads `TilemapManager` itself and renders every autotile kind and shape, every A1 animation frame, A5 and all six B–G sheets at 48, 32, 24 and 16, asserting that each rectangle is cut on the grid it belongs to, fills its cell exactly, stays inside its sheet — and, the load-bearing one, that the rectangle read at a smaller size is the rectangle read at 48 scaled by the same ratio the sheets themselves are. So a smaller project reads the same cells of the same layout, which is the whole claim.

- `EditorInstanceBroker`'s constructor threw in the web build, taking the editor down at boot with `Node module "os" is unavailable in RPG Reactor Web`. `WebHost` shims `fs`, `path` and `url` and throws for the rest, and the broker resolved `os` and `child_process` eagerly in its field initialisers — `start()` already returned false when any of them was missing, but construction never reached it. An `optionalModule` helper swallows the throw and yields null, so the broker declines on web exactly as it was written to. Coverage in `editor-instance-broker.test.cjs`, which loads the source against a require shim that behaves like the web host.
