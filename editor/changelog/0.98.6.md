- **"Can this battler use the item" and "is there any left" are now separate questions.** `Game_BattlerBase.meetsItemConditions` asked both in one line, so a plugin that prepays or waives an item's cost -- a pair consumed up front, a replayed action that costs nothing -- had no way to drop the stock check alone. It had to take over `meetsItemConditions` or `Game_Action.isValid` and reimplement the condition chain underneath, which means silently dropping any condition added to that chain afterwards: a plugin doing this against `VisuMZ_1_ItemsEquipsCore` reimplements that plugin's switch and JS notetag checks by hand, and stops honouring a third one the day it appears. `Game_BattlerBase.hasItemStock(item)` is now that half on its own, and `meetsItemConditions` calls it. Overriding it waives stock and nothing else -- occasion, can-move, and every condition another plugin has aliased onto `meetsItemConditions` keep running through their own chain, because the engine reaches the override from underneath them rather than in place of them. Nothing changes for anyone who does not override it: the default is the same `$gameParty.hasItem(item)` that was inline before, in the same position in the same expression.

- **A skill or item can hit a random number of times.** Repeats has always been one fixed number. It now has a **Max Repeats** box directly under it: set 2 and 4 and each use rolls 2, 3 or 4 hits, each equally likely. Leave the two equal and the count is fixed, which is what every skill and item authored before now keeps. The maximum takes a row of its own rather than squeezing in beside Repeats, because the form's value columns are too narrow to hold two stepper boxes in one cell.

  The range is stored as an optional `repeatsMax`, written only while it is above `repeats` and deleted as soon as it is not, so a fixed count saves exactly as it did before and a plugin that reads `repeats` directly sees the low end rather than nothing. Raising Repeats to or past the maximum collapses the range rather than leaving a maximum below the minimum on disk.

  The roll lives in the runtime, in a new `Game_Action.prototype.itemRepeats` underneath `numRepeats`, so everything that wraps `numRepeats` -- Attack Times+, a boost multiplier, a plugin's bonus hits -- works on the rolled count rather than replacing it. It is rolled once per action and kept on the action, keyed by the skill or item: `numRepeats` is read several times for one action (laying out its targets, AI scoring, plugins mid-action), and a fresh roll on every read would let those readings disagree. Using an item from the menu read `numRepeats` in its loop condition, once per pass; it now reads it once.

  A notetag that rewrites `repeats` when the database loads, such as VisuStella BattleCore's `<Repeat Hits: x>`, moves only the low end: below the maximum the range survives, at or above it the count is fixed. The Max Repeats label and its hint are a machine-assisted first pass across all 17 locales and want a native-speaker review.

- **The behaviour forecast no longer assumes one way of counting turns.** Reactor's `Game_Battler.turnCount` returns `$gameTroop.turnCount() + 1`, so the first battle turn is 1 and a condition gated on turn 0 can never hold -- which is exactly what the panel reported. `VisuMZ_3_BattleAI`'s on-the-spot mode drops that `+ 1` on a non-TPB system, and turn 0 becomes reachable, so the same panel would have called a working action dead.

  Whether that branch is actually taken cannot be settled at edit time: CoreEngine resolves the battle system through `$gameSystem.getBattleSystem()`, and a plugin command can change it mid-battle. So rather than guess an offset and print a confident wrong number, on-the-spot mode widens the searched turn range to include 0 and the panel says the counting can sit a turn earlier than it reads. Widening can only ever withdraw a warning, never invent one, which is the direction that keeps the "never fires" list worth trusting; a test asserts that the widened sweep always reports a subset of the narrow one. The Turn box takes its floor from the same place, and clamps to it rather than offering a turn the game cannot reach.

  Nothing changes for a project that is not running Battle AI, or is running it with on-the-spot mode off, which is its default.

- **An enemy's Action Patterns table now says which rows can actually be chosen.** The Rating column is the most misread number on that screen, because a rating means nothing on its own. `Game_Enemy.selectAllActions` takes the highest rating among the actions valid *at that moment* and throws away everything below a window measured down from it, so a row is invisible whenever a better-rated row is valid beside it -- and comes back the moment that rival cannot pay its cost. Nothing on the screen said so. A collapsible **Behaviour forecast** under the table now does: a what-if row for the variables that can actually change this enemy's outcome, the resulting rating ceiling, the surviving actions with each one's share, and a list of the rows that can never win with the reason for each.

  The reasons are separated rather than lumped into one warning, because they need different fixes: a skill id pointing at nothing, an occasion that excludes battle, a cost higher than the enemy can ever hold, conditions that never hold together, and being outranked. The last carries the lowest ceiling seen while the row was actually usable, which is what catches the case no one finds by reading: a cheap-looking rating-2 action costing 50 TP is dead not because 2 is low, but because any enemy holding 50 TP can also afford the rating-5 action above it. On the enemies in one project here the panel finds ten unreachable rows across four enemies, three of them in a single boss, and one enemy whose only action is gated on turn 0 -- a turn that never comes, since battle turns start at 1.

  Which window is in force is read from the project's plugin manifest, not assumed. `VisuMZ_3_BattleAI` replaces `selectAllActions` outright: its classic style keeps `rating >= max - variance`, a different comparison and a different width from the engine's `rating > max - 3`, and its random, casual and gambit styles do not use ratings the same way at all. A project running Battle AI at the default variance of 0 keeps only the highest valid rating, which makes strictly more rows dead than the engine would -- so a panel modelling the engine unconditionally would have been confidently wrong there. Conditions that plugins add through their own notetags stay outside the model, and the panel says so rather than quietly folding them in.

  The analysis is a standalone module, `src/utils/EnemyActionForecast.js`, with the runtime rule it mirrors pinned by a test, so the numbers cannot drift away from `selectAllActions` unnoticed. `DatabaseManager.getPluginManifest()` is the manifest reader the panel and the party-size lookup now share; it caches on the file's timestamp, because a manifest runs to megabytes on a large project and this one is consulted on every enemy click. The 17 new interface strings are a machine-assisted first pass across all 17 locales and want a native-speaker review.

- **A state that a plugin turns away is no longer reported as added.** `Game_Battler.addState` finds a state addable, calls `addNewState`, and then recorded the state on the action result and emitted `stateAdded` whether or not it had landed. `addNewState` is exactly where plugins refuse a state that was addable a moment earlier -- VisuStella Life State Effects' auto-life and death transform, and Auto Skill Triggers' death trigger, all return from it without adding death -- so the result went on listing a death that did not happen. The battle log queues a collapse for every death state it finds on a result, and collapsed an enemy that auto-life had just put back on its feet. Measured on a VisuStella project with Order Turn Battle: an enemy at 1 HP carrying an auto-life state and a bleed took its turn-end slip damage, auto-life restored it to 12,699 HP, and the log still called `performCollapse` on it -- the collapse sound played, the sprite dropped to nothing, and it faded back in over the next fifteen frames. It shows at turn end rather than on an ordinary killing blow because BattleCore's action sequences keep their targets immortal until the results have been displayed, so a death refused mid-action lands after the log has already read the result.

  `addState` now checks whether `addNewState` actually added the state. When it did not, nothing is recorded, no turn count is kept, and no event is emitted; `refresh` still runs, so whatever the plugin changed is settled. A state that lands, and a renewal of one the battler already has, is recorded and reported exactly as before.

- **A plugin can hand an action its targets ahead of time.** `BattleManager.startAction` rolls an action's targets with `makeTargets()` at the moment the action starts. A plugin that has to decide them earlier had one place to keep that decision: a `makeTargets` wrapper of its own, holding the chosen battlers and handing them back to the next caller. Two plugins in one project here do exactly that -- one tests pre-emptive reactions against the battlers a random scope actually picked, and has to make the resumed action hit those same battlers; the other replays a copied action onto the targets of the action it copies -- and both caches are spent by whichever code calls `makeTargets()` first. That need not be `startAction`: a target preview or a viability check asking the same question in between would take the answer meant for the action.

  `Game_Action.setPlannedTargets(targets)` now hands them to the engine, and `startAction` takes them in place of rolling -- once, and nowhere else, so every other `makeTargets()` call still gets a fresh answer and cannot use them up. `targets` is an array of battlers, or a function returning one that is called with the action as `this` when the action starts, for targets that must be checked again at that moment because a battler may have fallen in between. An empty result falls back to `makeTargets()`; `hasPlannedTargets` and `clearPlannedTargets` complete the set. The plan is kept in a `WeakMap` rather than on the action, so a JsonEx copy of the action -- which BattleCore makes for every forced action -- or a save file never carries battler references. Nothing changes for an action nobody plans: `startAction` calls `makeTargets()` exactly as before.
